## 應用情境

大專院校教室資源有限但使用需求頻繁，傳統紙本或人工登記容易導致資訊不同步、借用時間衝突（衝堂），且無法即時掌握教室使用狀況。本系統透過資訊化與資料庫管理方式，提供集中且即時更新的平台，讓使用者隨時查詢教室可用狀態、線上提交借用申請，並由管理員審核控管，同時具備自動衝突檢查、歷史紀錄保存與教室設備管理（含維修中狀態）等功能。

## 使用案例

**使用者（學生 / 教師）**
- 查詢教室：依日期、時間、設備需求查詢可用教室與人數限制
- 申請借用教室：填寫時間、教室代號、申請人資訊與用途，系統自動檢查衝堂
- 取消借用：僅限借用尚未開始、且申請人本人才可取消
- 查看借用紀錄：查詢個人或特定教室的歷史借用紀錄

**管理者（Admin）**
- 審核借用申請：Pending（審核中）→ Approved（核准）/ Rejected（拒絕，須填寫原因）
- 教室及設備管理：新增 / 停用教室與設備、設定教室為「維修中」（UnderMaintenance）

## 資料表設計

系統包含五張資料表：

| 資料表 | 說明 |
|---|---|
| User | 使用者：user_id、name、phone、role（S 學生 / T 教師 / A 管理員） |
| Room | 教室：room_id、room_name、location、capacity、status |
| Equipment | 教室設備：eq_id、eq_name、eq_desc、room_id、status |
| BorrowRequest | 借用申請：時間區間、借用類型、申請狀態、建立 / 審核 / 取消時間等 |
| AuditLog | 審核歷程：記錄審核者、操作（核准 / 拒絕）與原因 |

主要完整性限制：
- 同一教室在同一時間區間內，不允許兩筆 Approved 借用發生重疊（含長期借用的星期週期檢查）
- 維修中（UnderMaintenance）或停用（Disabled）的教室不可被核准借用
- 只有 role = 'A' 的管理員可以核准 / 拒絕借用申請
- 每筆核准或拒絕都必須在 AuditLog 中留下對應紀錄
- 取消借用為申請人本人操作，記錄於 BorrowRequest.cancelled_at，不計入 AuditLog

完整的 ER Diagram 與資料表欄位規範（含 Domain 限制）請見報告內文。

## 資料庫 Schema

使用 MySQL 語法撰寫，五張資料表皆設定主鍵、外鍵、CHECK 條件與預設值，確保資料一致性（如 status 合法值限制、時間先後順序檢查、借用類型與 weekday 對應等）。

## VIEW 設計

系統設計七個 VIEW，提供應用程式層直接查詢所需的邏輯視圖：

| VIEW 名稱 | 用途 |
|---|---|
| v_available_rooms | 篩選可借用教室（含位置、容納人數） |
| v_borrow_summary | 借用申請總覽（JOIN 申請人與教室名稱） |
| v_pending_requests | 待審核申請清單（含聯絡電話） |
| v_room_equipment | 各教室設備盤點 |
| v_audit_history | 審核歷程（JOIN 管理員、申請人、教室） |
| v_room_borrow_stats | 各教室借用統計 |
| v_user_borrow_stats | 各使用者借用統計 |

## Trigger 設計

實作兩個 BEFORE INSERT Trigger，處理無法單純以 CHECK 條件完成的跨列邏輯驗證：

- **trg_check_overlap（衝堂檢查）**：新增借用申請時，自動檢查同一教室、同一日期是否已有時間重疊的 Approved 紀錄，若有則以 SIGNAL 拒絕新增
- **trg_check_maintenance（維修中教室限制）**：新增借用申請時，自動檢查目標教室是否處於維修狀態，若是則以 SIGNAL 拒絕新增

兩個 Trigger 皆已實際測試驗證，攔截時顯示中文錯誤訊息。

## 實作環境

於 MariaDB（Docker 環境）中建置，包含資料庫與資料表建立、範例資料新增、多表 JOIN 查詢、VIEW 建立與查詢、完整性限制測試（CHECK 條件與外鍵約束）以及 Trigger 測試的完整流程。
